# Current state — Phase 2b v0.13 (cx CARRY4 pipeline, clk_sys 150 MHz)

Session date: 2026-05-15.

## Overall goals

See [docs/zynq-architecture.md](./zynq-architecture.md) for the full plan.
In short: replace the Efinix Ti60 + STM32N6 dual-chip design with a single
Zynq-7020 SoC (on a Z-Turn SOM), targeting ~$150/board at ≤100 units.

## What exists

### Top-level module: `fpga_xt_top` (hdl/fpga_xt_top.sv)

Integrates the main SALLY CPU stack + ANTIC video pipeline across three
clock domains generated from a single 50 MHz reference by MMCME2_BASE:

| Domain    | Frequency    | Drives |
|-----------|-------------:|--------|
| clk_sally | 100.000   MHz | sally_core, sally_mem, sally_clock |
| clk_sys   | 150.000   MHz | antic_top.clk_bus, fb_scanout AXI fetch FSM, xt_blitter, AXI HP stub |
| clk_pix   | 148.4375  MHz | fb_scanout vbeam + line-buffer read + 8888→565 Bayer dither; RGB565+sync to SiI9022A (≈ 148.5 MHz CEA-861 1080p60, -0.042 % error) |

Two MMCMs sit at the head of the clock tree:
- **MMCM #1** — VCO=1200 MHz (×24 from 50 MHz); CLKOUT0 /12 → clk_sally,
  CLKOUT1 /8 → clk_sys.
- **MMCM #2** — VCO=1187.5 MHz (×23.75 from 50 MHz); CLKOUT0_F /8.000 →
  clk_pix. Dedicated so MMCM #1 keeps clean integer 100/150 outputs.

Each domain has an async-assert / sync-deassert reset pipeline gated by
`rst_n & mmcm1_locked & mmcm2_locked`.

Top-level ports: `clk_50`, `rst_n`, `rgb_*` (parallel RGB565+sync to
SiI9022A), `uart_*` (debug UART through PS MIO), and a 4-bit `dbg`
observability bus.  The three AXI master ports (banked-window reader,
fb-scanout, blitter) are no longer exposed externally — they route
through an internal `zynq_ps_hp_stub` module that provides AXI3 slave
targets for OOC synthesis.  For bitstream builds, the real PS BD wrapper
(`ps_bd_wrapper.v` generated by `gen_ps_bd.tcl`) replaces the stub as
the top-level, with fb_scanout → HP0 and xt_blitter → HP1.

CDC infrastructure (all in `hdl/`):
- `cdc_fifo_1w1r` — SALLY hwreg writes (clk_sally) → ANTIC bus (clk_sys).
  4-deep async FIFO; ANTIC side regenerates a 1-cycle bus_addr / bus_data
  / d0xx_n / d4xx_n write strobe per popped descriptor.
- `cdc_sync_bit` — ANTIC status (NMI/IRQ/HALT) → SALLY (2-FF, dst_clk_sally).
- vbeam pix-domain signals are CDC-synced inside antic_top.
- fb_scanout `line_start` (clk_pix → clk_sys): toggle + 2-FF + edge
  detect for the AXI fetch trigger. Dual-port BRAM line buffer crosses
  data clk_sys → clk_pix natively.

Sub-systems:

1. **SALLY CPU** — Arlet 6502 core + sally_mem (64 KB BRAM, dual-port for
   ANTIC DMA reads) + sally_clock (RDY gating) + banked_axi_reader (AXI
   master for DDR3-backed banked-memory window, tied off for Phase 1).
2. **ANTIC video pipeline** — full ANTIC/GTIA/POKEY chain with DL parser,
   compositor, GTIA colour resolution, line buffer, scan-out, palette LUT,
   and parallel RGB565 + sync output. Pipeline still synthesises and
   runs, but its `rgb_o` outputs are observed only at Phase 2a — the
   pads are now driven by `fb_scanout`. A future mode mux will route
   ANTIC in for legacy-Atari mode with a 5× pillarbox upscaler.
3. **DDR3 framebuffer scan-out** (`fb_scanout`, new in Phase 2a) — vbeam
   at 1080p60 + AXI4 read master (HP port) + ping-pong line buffer
   (2×1024×64 bit BRAM) + 8888→565 4×4 Bayer dither. Reads the
   RGBA-8888 framebuffer at 0x3000_0000 (per
   [memory-map.md](./memory-map.md)) line-by-line through 64 × 16-beat
   AXI3-friendly bursts; output drives the rgb_* pads to the SiI9022A.
4. **xt-blitter** (`xt_blitter`, v0.10) — rect fill + line draw + block blit +
   **nearest-neighbour**, **bilinear scaled blit**, **alpha-blend rect fill**,
   and **font raster** with RGBA-8888 pattern memory, phase offset,
   alpha-aware transparent pixel masking, 16-beat AXI4 write bursts,
   single-pixel AXI4 reads, and a separate font-coverage BRAM.
   Register interface spans $D4B0..$D4BF and $D4C0..$D4CF, tapping the same
   clk_sys-side hwreg bus that ANTIC sees.

   - **Rect fill** (CMD=0x01, optional FLAGS.BLEND for alpha-blend):
     2-pixel-per-beat accumulation, burst packing, zero-opacity skip.
     Pattern memory is up to 1024×32-bit (one RAMB36E1, addressable as
     2^log_pw × 2^log_ph for any log ∈ [0..5], i.e. 1×1 up to 32×32)
     loaded by SALLY byte-stream writes via $D4BB; writing PAT_LOG_W
     at $D4BA resets the load pointer.
   - **Line draw** (CMD=0x02): DST_W/H hold signed DX/DY deltas.
     Bresenham algorithm with signed error term, simultaneous X/Y stepping,
     single-beat AXI writes per pixel.  Pattern lookup uses offset from
     line start for consistent tiling.  Pixel-accurate endpoint detection.
   - **Block blit** (CMD=0x03): Copies a rectangular region from
     (SRC_X,SRC_Y) to (DST_X,DST_Y) with the given WIDTH×HEIGHT.
     Row-by-row, segmented into up to 32-pixel (16-beat) AXI read→write
     bursts through HP1.  Straight copy (all bytes valid, no pattern)
     when RASTER_OP = 3/15; supports all 16 GEM raster ops via $D4BF:
     ops 0/5 skip, op 12 (~SRC) inverts bytes during the source read,
     and ops needing destination data (1,2,4,6,7,8,9,10,11,13,14) add
     a second AXI read segment per blit segment for byte-wise combine.
     Constraints: src_x[0]==dst_x[0], width even.
   - **Scaled blit (NN/bilinear)** (CMD=0x04, qualify with FLAGS.BILINEAR;
     also CMD=0x06 for legacy compat): Nearest-neighbour or 2×2 tap
     bilinear scaling.  Single-pixel AXI reads with Bresenham-like
     incremental stepping.  Bilinear path reads four 4-byte AXI beats
     per destination pixel via compact sub-pixel-counter FSM, followed
     by 8-cycle sequential divider for 8-bit fractional weights and
     weighted blend (all 8×8→16 multipliers in LUTs, 0 DSPs).
     **FLAGS.BLEND** (with or without BILINEAR) enables destination-read
     + alpha-blend: checks source alpha per pixel — α=0 skips (wstrb=0),
     α=255 writes opaque (current fast path), 0<α<255 reads destination
     via single-beat AXI read and blends via SC_SBLEND state (reuses
     same blend arithmetic as BL_RACC).  Bilinear path interpolates
     alpha from the four tap pixels (a_blend) instead of hardcoding
     8'd255, enabling proper semi-transparent bilinear compositing.
   - **Font raster** (CMD=0x05, NEW in v0.7): Composites glyph alpha
     coverage (from dedicated 512×32-bit font BRAM, packed AAAA) with
     RGBA pattern texture.  Alpha = (coverage × pattern_A) >> 8.
     Reuses the same blend pipeline (BL_RACC) as alpha-blend rect fill.
     Supports opaque/transparent shortcuts.  Font data loaded via
     FONT_DATA byte-stream writes ($D4CE); FONT_CTRL ($D4CF) resets
     the load pointer.  Max glyph: 32 rows × 64 pixels.
   - **FLAGS register** ($D4C8): 8-bit qualifier — bit 0 = BLEND
     (alpha-blend with destination for CMD=0x01), bit 1 = BILINEAR
     (bilinear filtering for CMD=0x04), bit 2 = FONT (selected by
     CMD=0x05 internally).  Bits 7:3 reserved.
   - **STATUS register** ($D4BD, read-only): bit 0 = busy (1 while
     blitter FSM active, 0 when idle).  Bits 7:1 read 0.  Polled by
     the PS to wait for command completion.  Synchronised from clk_sys
     (blitter domain) to clk_sally (SALLY read domain) via a 2-FF CDC,
     so busy status may lag by up to 3 clk_sally cycles — safe for
     polling.
5. **Peripheral I/O** — PIA shadow ($D300), joy_bridge (PCAL9722 SPI),
   peri_bridge (SIO + POT), PCM1808 stereo I²S ADC, bus-snoop for M-PBI
   cart/PBI bus mastering.

### Bugfix (v0.4) and breaking change (v0.7)

**Register address decode (v0.4)** — `reg_addr` was incorrectly using
`bus_addr[4:0]` which mapped $D4Bx to reg_addr≥16 (no match) and $D4Cx
to reg_addr 0-3 (misread as DST_X/DST_Y).  Fixed to `{bus_addr[5],
bus_addr[3:0]}` — $D4Bx maps to reg_addr 0-15, $D4Cx maps to reg_addr
16-31.  The blitter register interface was non-functional before this fix.

**Address mapping fix (v0.7, breaking)** — The v0.4 fix inverted the bank
mapping: `bus_addr[5]`=1 for $D4Bx, giving reg_addr 16-31 (SRC bank), while
`bus_addr[5]`=0 for $D4Cx, giving reg_addr 0-15 (DST/PAT bank).  This
reversed the documented register layout.  In v0.7 the formula is corrected
to `{~bus_addr[5], bus_addr[3:0]}`, restoring $D4Bx → DST/PAT/CMD (0-15)
and $D4Cx → SRC/FLAGS/FONT (16-31).  Any PS software written for the
v0.4–v0.6 behaviour must update its register addresses.

## Timing — three domains, post-route OOC (Phase 2b v0.13, all features, clk_sys 150 MHz)

```
Intra-clock:
  clk_sally   (100.0000 MHz)  WNS +0.651   WHS +0.125    1029 endpoints  ✅
  clk_sys     (150.0000 MHz)  WNS +0.312   WHS +0.059    5649 endpoints  ✅
  clk_pix     (148.4375 MHz)  WNS +2.407   WHS +0.159     110 endpoints  ✅

Inter-clock: no inter-clock paths constrained (set_clock_groups
-asynchronous not matching generated clock names).
```

**clk_sys at 150 MHz timing-closed** with WNS = +0.312 ns (0 failing
endpoints).  The cx CARRY4 pipeline successfully broke the previous
critical path from cx_reg[0] → CARRY4×6 → LUT6×6 → state_reg[1] that
limited the 133 MHz build to WNS +0.477 ns (12 logic levels, 6.862 ns
data path).  The new critical path is the line-draw Bresenham engine:
`line_dy_reg[0] → 9× CARRY4 + 5× LUT → line_err_reg[13]` at 14 logic
levels, 6.282 ns data path (62 % logic, 38 % route), slack +0.312 ns.

**clk_sally at 100 MHz** timing-closed at WNS = +0.767 ns
(0 failing endpoints).  The critical path is a BRAM read-to-write path
through the SALLY CPU ALU address decoder (7 logic levels, 8.704 ns
data path, 55 % route delay).

### Fixes applied in v0.13

1. **Pipeline cx CARRY4 chain** — The critical path at 133 MHz was
   `cx_reg[0] → CARRY4×6 (cx+1 >= dst_w) → LUT6×6 (state decode) →
   state_reg[1]` with 6.862 ns data path (62.4 % route).  Added
   `cx_ge_dst_w_q` register that captures `(cx + 16'd1 >= dst_w_q)` in
   S_ACCUM_W (alongside `cx_q <= cx`), breaking the CARRY4 chain out of
   the S_ACCUM_W2 state-decode path.  The comparison now feeds a single
   registered bit instead of recomputing through 6 CARRY4 levels.  Cost:
   +1 FF, +0 LUTs.

2. **clk_sys raised to 150 MHz** — MMCM #1 CLKOUT1_DIVIDE changed from
   /9 (133 MHz) to /8 (150 MHz).  POKEY_CLK_BUS_HZ → 150_000_000;
   I2C prescale → 750.  Build in progress.

### Fixes applied in v0.12

1. **Pipeline BL_RACC / SC_SBLEND (option 1)** — The alpha-blend critical
   path (`bl_src_pixel_q[0] → blend multipliers → CARRY4s → burst_data`)
   was split into two cycles: cycle 1 computes the blend and registers the
   result in `bl_blend_q`; cycle 2 uses `bl_blend_q` for the burst-buffer
   write.  This breaks the combinational path through the 8×8→16 multiply-
   accumulate cloud, adding a clean register boundary.  Both BL_RACC and
   SC_SBLEND (scaled-blit blend) were split, with new states BL_RACC2 and
   SC_SBLEND2.  Cost: ~33 FFs, +1 cycle latency per blended pixel.

2. **AXI register slice at PS boundary (option 2)** — Added a 2-deep
   register pipeline on every AXI signal between the xt_blitter HP1
   master and the PS block design's HP1 slave port (inside `ifdef
   USE_PS_BD` for the bitstream build; OOC path unchanged).  This cuts
   the path through the PS address decoder CARRY4s
   (`processing_system7_v5_5` address decoder logic).  Covers all 5
   AXI channels (AW, W, B, AR, R) in both directions.  Cost: ~80-100
   FFs, 2-cycle additional latency per transaction (absorbed by AXI
   handshake).

### Fixes applied in v0.11

1. **`(* keep = "true" *)` on `font_pixel_q2`** — Without this attribute,
   Vivado absorbed both `font_pixel_q` and `font_pixel_q2` into the BRAM's
   DO_REG cascade (RAMB18E1 internal pipeline registers), making the
   two-stage pipeline a no-op.  The timing path went through the BRAM's
   combinational output (0.734 ns) directly into the state-decode cloud
   with no external register break.

2. **Moved 8×8 multiplier to `S_ACCUM_WAIT`** — The modulated-alpha
   computation `ft_al = (font_coverage × pattern_alpha) >> 8` was
   previously computed in `S_ACCUM_W` as part of the same combinational
   cloud as the alpha comparison (==0 / ==255) and state-transition
   decode.  Moving it one cycle earlier (into `S_ACCUM_WAIT`, where both
   `font_pixel_q2` and `pat_pixel_q2` are already valid for font mode)
   reduced the critical path in `S_ACCUM_W` to just the 8-bit comparator
   + state mux (~3-4 LUT levels), well within 6.667 ns.

### fmax bottleneck

The alpha-blend path that was the WNS bottleneck at 100 MHz (bl_src_pixel_q
→ blend multipliers → CARRY4s → PS address decoder → burst_data_reg,
WNS = +0.023 ns) is no longer the critical path.  The BL_RACC pipeline
split + AXI register slice have shifted the bottleneck to the SALLY CPU
internal BRAM read-to-write path: `mem_reg_0_3 → ALU address decode →
mem_reg_1_6 ENARDEN` (7 logic levels, 8.704 ns data path, 55 % route),
which caps clk_sally at ≈ **115 MHz**.  On clk_sys the worst path is a
reset fanout (6.407 ns, route-dominated) giving ≈ **130 MHz** ceiling.

### Phase 5 (forward-looking) — Stack efficiency & multitasking

Design specs completed (not yet implemented), ordered by dependency:

1. **6502 stack embellishments** ([docs/6502-embellishments.md](./6502-embellishments.md))
   — 4 KB hidden stack RAM (top 256 bytes aliased to $0100–$01FF), 12-bit SP,
   9 SP-relative instructions, and PSH/PLL for atomic register save/restore +
   local frame allocation.  All opcodes in the $x2 JAM column, 5-cycle PSH/PLL
   using dual-port BRAM.  This is about **C-calling-convention efficiency**
   on a single task (replacing software stacks in zero-page with hardware
   stack frames).  Independent of multitasking.

2. **Banked-stack context switching** ([docs/banked-stack-context-switch.md](./banked-stack-context-switch.md))
   — 8 × 4 KB stack banks in BRAM (32 KB total), with 1 sacrificed as a
   permanent DDR3 landing pad (Free slot).  Up to 7 tasks resident (1 Active
   + 6 Resident) with LRU eviction in the background.  Cold load is ~3.4 μs
   (load only — no eviction needed before loading).  Builds on the 12-bit SP
   and internal stack RAM from (1) to add **multitasking context-switch
   support**.

Implementation deferred until after Phase 4, as the current FreeRTOS + LVGL
pipeline (Phase 3) runs entirely on the Cortex-A9s and doesn't need SALLY
CPU stack enhancements.  Phase 5 applies when SALLY itself hosts a
multitasking kernel or when C code compiled for the 'xt' model runs on the
bare metal.
