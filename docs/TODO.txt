DDR3 banked window (parallel track -- NOT required for boot-to-BASIC)
=====================================================================

  Boot runs from flat BRAM (bank 0). DDR3 backs the extended-arch
  banked pages, bank index from $D5C0 (code) / $D5C1 (data). Because
  a normal boot (bank 0, ROMs on) never touches DDR3, "DDR3 working"
  must be proven by an explicit bank-switch test, not by reaching the
  prompt. Wiring it up:

  1. Connect sally_mem's AXI master to a real HP port -- it is hard
     tied-off today (dead wires fpga_xt_top.sv:322-327, instance ports
     :669-690). Add HP2 on the PS BD (still PCW_USE_S_AXI_HP2=0).
     The master runs on clk_sally (100 MHz); each HP port has its own
     aclk, so clock HP2 at clk_sally to avoid an AXI clock converter.
     Needs the AXI4->AXI3 burst-len handling the blitter's HP1 path
     already does (8-beat arlen=7 fits AXI3's 4-bit len field).

  2. *** CODE PAGES MUST BE WRITABLE. *** banked_page_cache's code
     cache is currently READ-ONLY (banked_page_cache.sv:5-7; a code
     write is a no-op at :290-291). The legacy machine treats
     $6000-$9FFF as ordinary RAM, and extended code banks need the
     same writability. Make the code cache read-write with dirty-bit
     write-back on page swap, exactly like the existing data cache
     (DATA_FLUSH_* FSM + read-allocate-on-write-miss). Without this,
     a code-window write to a non-zero bank silently vanishes: the
     shadow BRAM gets it but the cache read path returns stale DDR3
     data.

  3. Reserve the DDR3 region: 0x2000_0000 code / 0x2040_0000 data
     (sally_mem.sv:75-76) vs the framebuffer at 0x3000_0000. Keep the
     PS (FSBL/app, later Linux) out of 0x2000_0000-0x207F_FFFF.

  4. Validate with a bank-switch test (boot won't exercise DDR3):
     set $D5C1=1, write a pattern across $A000-$BFFF, switch to bank 2
     and back, verify the data survived the page swap. Repeat on the
     code window ($D5C0) once code writes work, to prove req #2.
